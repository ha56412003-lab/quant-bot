# 持仓强弱雷达（Radar）—— 2026-11-07

> 一句话：**只在持仓币上跑的一套分钟级打分，告诉你这个仓还有没有劲，要不要手动走。**
> 它不参与任何交易决策，量化系统该怎么跑还怎么跑。

---

## 一、为什么做这个

浩哥的原话：

> 持仓的票总是被回撤，有没有可能真做一个雷达系统，按分钟级别去扫描持仓的 B（特别是在盈利的 B），
> 雷达就做一件事，通过指标判断持仓 B 的走势强弱，然后给人工判断要不要手动平仓（平一半 / 全平）。
> **等于这套系统只起到提示作用，不干预正常量化系统的走势。**

### 动手前的数据诊断（很重要，先看这个）

在做系统之前，先用 20 个币 / 60 天 / 1,031 笔回测验证了一件事：**「被回撤打掉」到底是不是坏事？**

结论是——**不是，回撤出场反而是唯一赚大钱的出场类型**：

```
「均线破+回撤」出场 731 笔，合计 +210.45R

如果一律多等 8 小时：+73.51R → −67.60R   净亏 141R
如果一律多等 4 小时：+73.51R →  −7.80R   净亏 81R
```

原因：出场后价格确实还会朝有利方向冲（后 8h 中位 +0.57R），
但 **8 小时结束时又回到出场价附近（中位 −0.01R）**——那是冲高假象，赚不到手。

**所以雷达的目标不是「多等一会儿」，而是「分辨这次回调会不会有第二波」。**

### 为什么不用 K 线

同样用这 731 笔，把出场时刻所有能从 K 线拿到的特征全部试了一遍，
去预测「出场后 8h 是否还能冲过 1R」（基准命中率 32%）：

| 特征 | 命中率 |
|---|---|
| 出场时浮盈 >2R | 59% |
| 放量回调（>3 倍均量） | 53% |
| 刚破均线 2~3 根 | 50% |
| 回撤幅度 / ATR 收缩 / 缩量 | ≈32%，等于没用 |

最好只有 50%，而且「放量反而更容易有第二波」这种反直觉结果，
八成测的是**波动率**而不是**方向**——选出来容易涨的，同样容易反向崩。

**结论：光看 K 线，雷达做出来是安慰剂。所以全部改用订单流。**

## 二、指标选择：为什么这几个"不滞后"

浩哥的要求是「**不能是那种滞后很严重的指标**」，这是硬约束。

传统技术指标（MA / MACD / RSI）的本质是对过去价格做平滑，**天生滞后一个周期**，
等它转向，行情已经走完了。所以本系统一个都不用。

改用「成交层」的即时数据——K 线是结果，订单流是原因：

| 维度 | 权重 | 数据源 | 周期 | 滞后 | 在判断什么 |
|---|---|---|---|---|---|
| **主动买卖比** | 25 | Binance taker | 5m × 3根 | ≤5 分钟 | 谁在主动成交 |
| **CVD 背离** | 25 | Clawby cvd | 5m × 6根 | ≤5 分钟 | 价格和主动资金是否同向 |
| **OI 变化** | 20 | Binance OI | 5m × 2根 | ≤5 分钟 | 新钱进场，还是空头回补 |
| **清算** | 15 | Clawby 三所聚合 | 1h 桶 | ≤1 小时 | 自己人正在被打爆多少 |
| **盘口失衡** | 15 | Clawby orderbook | 实时 | 实时 | 挂单往哪边压 |

> 曾用过的两个指标已删除：**大户多空比**（24 小时变化，严重滞后）、
> **CVD 12 小时斜率**（更滞后）。第一版就是栽在这两个上的。

### 各维度的判断逻辑

**主动买卖比** —— 最近 15 分钟买盘/卖盘谁主动。做多时比值 <1 就是卖盘在打。

**CVD 背离**（最关键的信号）：

```
多头：价涨 + CVD 涨 = 真有人接钱进来   → +1.0
多头：价涨 + CVD 跌 = 虚涨，随时回落   → −1.0   ← 最强离场信号
多头：价跌 + CVD 涨 = 砸下去有人吸     → +0.6
多头：价跌 + CVD 跌 = 一起走            → −0.6
空头全部镜像。
```

**OI 变化** —— 涨是「新钱推的」还是「空头回补」：

```
多头 + 价涨 + OI 涨 = 新资金进场（最强）    +1.0
多头 + 价涨 + OI 跌 = 空头平仓推上去（油尽） +0.3
多头 + 价跌 + OI 涨 = 空头在加仓（危险）    −1.0
多头 + 价跌 + OI 跌 = 多头止损离场（跌势尾声）−0.3
```

**清算** —— 同向持仓的清算倍数远高于反向，说明这一侧正在被强平踩踏。
**注意有 20 万 U 绝对量门槛**：清算量太小时倍数是纯噪音，第一版没门槛的时候，
几十美元的清算都能把 15 分权重整个打满。

**盘口失衡** —— bids/asks >1 下方接盘厚。挂单可以撤，所以只当辅证，权重低。

## 三、打分与档位

```
raw   = Σ(维度分 × 权重) / Σ权重        # −1 ~ +1，缺的维度按剩余权重重分配
score = 50 + 50 × raw                  # 0 ~ 100
```

缺数据时**按剩余权重重分配**，不是简单补 0——否则缺一个因子会把总分误判成中性。

| 分数 | 判定 | 建议 |
|---|---|---|
| **80–100** | 走势很强 | 势还在，不用动 |
| **60–80** | 走势放缓 | 开始放缓，盯着点 |
| **40–60** | 走势转弱 / 中性偏弱 | 浮盈 >0.3R → 可以考虑平一半；否则观望 |
| **<40** | 走势力竭 | **浮盈时：建议手动平掉（至少平一半）**；浮亏时：交给系统止损 |

**浮亏时不给离场建议**——那是量化系统止损该管的事，雷达不越界。

### 分数分布校准（实测）

拿 18 个活跃币此刻的真实行情跑了一遍（做多/做空各一次）：

```
SOL  做多 86.0   ← 80+ 很强
LINK 做多 81.6   ← 80+ 很强
BNB  做多 79.8
XRP  做多 78.1
DOGE 做多 73.8
ADA  做空 72.4
BTC  做空 61.0
ETH  做多 51.6
DOGE 做空 26.2
ADA  做多 27.4
ETH  做空 23.5
SOL  做空 14.1   ← 40 以下力竭
```

**分布 14 ~ 86，四个档位全部能触发，不需要放大映射。**
做多/做空分数自然互补（SOL 做多 86、做空 14），说明打分逻辑自洽。

## 四、边界：它绝对不能做什么

| 允许 | 禁止 |
|---|---|
| 读 `positions` 表 | 写 `positions` / `trades` |
| 采因子、算分 | 调 `engine` 平仓、改 `strategies` 参数 |
| 写自己的 `radar_history` 表 | 影响任何交易判定 |
| 前端显示分数 | 自动下单 |

代码层面：`backend/radar.py` **一行都不 import** `strategies.py` / `engine.py`。
独立循环，跑挂了不影响交易，交易挂了它也跟着没意义（但互不拖累）。

前端：持仓表格「币种」单元格里一个小徽章（不新增列，避免横向滚动）：

```
BTC ●88↑
```

- 数字 = 分数，箭头 = 跟自己上一条比（↑变强 / ↓转弱 / →走平）
- 颜色四档：青绿(80+) / 黄(60-80) / 橙(40-60) / 红(<40)
- 鼠标悬停显示判定和建议动作

**注意**：徽章配色是「走势强弱」的独立色阶，**不是红涨绿跌**。
红色在这里表示"力竭/危险"，和浮盈的红色是两套语义，位置也不同不会混。

## 六、下一步：怎么验证它到底有没有用

现在它是"只观察"，还没证明有效性。攒 2-4 周数据后用真实持仓回答两个问题：

1. **分数低的仓，后来是不是真的走弱了？**（看分数 <40 之后 1-4 小时的 R 变化）
2. **如果按雷达建议减仓，总收益会不会更好？**（对照：实际出场 vs 按分数出场）

验证通过 → 可以谈要不要接进出场规则；
验证不通过 → 承认这条路走不通，雷达留着当仪表盘，不硬推。

**在验证完成之前，不要拿它改任何交易参数。**

## 七、执行层：什么时候叫、叫几次、叫完怎么验

> 光有分数没用 —— **每分钟报一个数字，等于没报**。
> 执行层要解决三件事：不刷屏、给动作、能验证。

### 1. 只在「跨档往下掉」时叫一次

分数每分钟都在动，如果在 55~59 之间来回抖就叫两次，两天就把人喊麻了。

规则：
- **同档位内抖动不叫**（55→48 都在「转弱」档，不叫）
- **跨档往下掉才叫**（75→55 从「放缓」掉进「转弱」，叫一次）
- **同一币 30 分钟内不重复叫**（冷却）
- **但如果这次比上次更严重，穿透冷却** —— 「55 掉到 55」不该刷屏，
  但「55 再掉到 35」是要命的事，必须出声
- **分数回升不叫**（那不是警报，是恢复）
- **第一次见到某个币不叫**（没有"变化"可言，只记状态）

### 2. 直接给可执行的动作，不给形容词

| 分数 | 浮盈 | 动作 | 话 |
|---|---|---|---|
| 80+ | — | 不提醒 | 势还在，不用动 |
| 60-80 | — | 不提醒 | 开始放缓，盯着点 |
| 40-60 | ≥1.5R | **平一半** | 浮盈够厚，可以考虑平一半落袋 |
| 40-60 | <1.5R | 观望 | 走势转弱，等下一轮确认 |
| **<40** | ≥1.0R | **平一半** | 力竭但利润厚：平一半锁利润，剩下交给系统 |
| **<40** | 0.3~1R | **全平** | 力竭且利润薄：扛不住回撤，建议全平 |
| **<40** | <0.3R | 交给系统 | 没浮盈，不掺和，交给系统止损 |
| **<40** | 浮亏 | 交给系统 | **雷达绝不在浮亏时喊离场** |

最后两行是刻意设计：浮亏时的止损是量化系统的活，雷达插手只会打乱系统节奏。

### 3. 叫完要能验证准不准

每条警报落 `radar_alerts` 表，1 小时后自动回填：

```
eval_1h_r / eval_4h_r = 提醒后，朝【持仓有利方向】的涨跌幅（%）

  负数 → 之后继续朝不利方向走  → 提醒是对的
  正数 → 之后反弹了            → 提醒早了
```

攒够样本后直接能回答：「雷达喊平仓的那些仓，后来真的走弱了吗？」
**这是判断雷达到底有没有用的唯一凭据，不看感觉。**

### 6. 修掉的两个真 bug（空仓时看不出来的）

| bug | 后果 |
|---|---|
| `scan_once` 残留已删除的 `_last_slow` / `SLOW_SEC` | **一旦有持仓立刻 AttributeError**，雷达整个不工作 |
| `p.get("mark_price")` —— positions 表根本没这个字段 | 浮盈恒为 0，所有动作建议全部走错分支（永远「交给系统止损」） |

第三个语义坑：`verdict_of` 和 `_advice_action` 各写一套阈值，出现
「页面建议平掉、警报说交给系统」的矛盾 → 已统一为单一来源。
