# 持仓操作区功能改造 · 2026-11-05

## 一、修掉的真 BUG（不止用户报的两个）

### BUG 1 · `api.post` 不存在 —— 4 个功能同时失效

**现象**：点「调整杠杆」报错、单仓平仓报错、一键全平报错、日目标重置报错。

**根因**：`src/api.js` 里 `post` 是**独立命名导出**，但 `api` 对象里没挂 `post`：

```js
export { post }        // 单独导出
export const api = {  /* 没有 post！ */ }
```

前端调用 `api.post(...)` → `undefined is not a function`。

**修复**：`api` 对象里加 `post, get,`。

**影响面**：4 处调用全部恢复正常
- `Dashboard.jsx:70` 一键全平
- `Dashboard.jsx:78` 杠杆调整
- `Dashboard.jsx:86` 单仓平仓
- `RiskPage.jsx:83` 日目标重置

### BUG 2 · 追加保证金输入框是死的

**现象**：输入数字后没反应、无确认、不生效。

**根因**：`<input>` 只写了 `placeholder` 和样式，**没有 `value` / `onChange` / 任何事件**。纯装饰元素。

**修复**：受控组件 + 回车/失焦提交 + 二次确认弹窗。

### BUG 3 · 后端 `Body` 未导入（改造中新引入，已当场发现）

新增 `body: dict = Body(...)` 时忘加 import，Pyright 报 `"Body" is not defined`。补齐 `from fastapi import Body, FastAPI, HTTPException`。

## 二、新增功能

### 1. 分批平仓（全平 / 一半 / 1/3）

**后端** `executor.close_position(pos, price, reason, fraction=1.0)`：
- `fraction >= 0.999` → 原全平逻辑
- `0 < fraction < 1` → **只减仓，仓位保持 open**：
  - `qty` 按比例扣减
  - `extra_margin` 按比例扣减
  - `trades.kind = 'partial_close'` 单独记账
  - 校验：P&L 只按平掉的那部分数量算

**接口** `POST /api/positions/{pid}/close`，body `{"fraction": 0.5}`。

### 坑 1 · `positions` 表没有 `margin` 列

**教训**：在**真实数据**上测写操作，测完必须能回滚。要么先备份 db，要么记下原值。

# 附加修复 · 监控池「易插针」误杀（2026-11-05 上午）

## 现象

监控池 30 个币，**28 个被判「易插针」**，只剩 INJUSDT 一个能交易。
日志：`quality refreshed: 29 symbols, pass 1`

真正危险的不是少赚，而是**现有 6 个仓位平掉后，新信号会全部因"易插针"开不了仓，策略实际停摆**。

## 根因

`backend/quality.py` 的插针算法：

```python
spike = max(high - low for x in bars[-96:]) / atr   # 96 根 15m K线 = 24 小时
```

**问题在数据源周期**：15 分钟 K线噪音极大，96 根里每根都可能是长影线十字星。
实测 29 个币的 spike 值**全部落在 4.0 ~ 8.4**，而阈值是 3.5 —— 等于整个池子判死刑。

**不是阈值定错，是度量尺子选错了。**

## 排查过程（三轮实测，不能拍脑袋）

| 方案 | 结果 | 结论 |
|---|---|---|
| ① 15m 的 90 分位 | 所有币 1.67~2.76 | ❌ 无区分度，29/29 全过 = 没过滤 |
| ② 15m 的影线占比 / 长影线根数 | 影线占比全 ≈0.95；长影 23~42 根 | ❌ 15m 上所有币都"像插针" |
| ③ **1h 的 max振幅/ATR（96 根 = 4 天）** | **2.08 ~ 8.33，正常币 2.1~3.5** | ✅ **有区分度** |

## 修复

```python
bars  = await binance.klines(sym, "1h", 100)   # 15m → 1h
qv    = sum(volume * close for x in bars[-24:])  # 24 根 1h = 24 小时成交额
spike = max(high - low for x in bars[-96:]) / atr # 96 根 1h = 4 天窗口
MIN_ATR_PCT: 0.3 → 0.6                          # 口径从 15m 换 1h，ATR 约大 2 倍
MAX_SPIKE:   3.5 保持不变
```

**顺带修的两个口径 bug**：
- `qv` 原来用 `bars[-96:]`，在 1h 口径下会变成 4 天成交额（放大 4 倍），已改为 `bars[-24:]`
- `MIN_ATR_PCT` 未随周期换算，会导致所有币被判"死水"

## 结果

| | 修复前 | 修复后 |
|---|---|---|
| 通过币数 | **1** | **26** |
| 被拦 | 28 个「易插针」 | 3 个（见下） |

**被拦的 3 个，每一个都拦得对**：

| 币种 | 插针值 | ATR% | 成交额 | 拦截理由 |
|---|---|---|---|---|
| TRXUSDT | **8.33** | 0.27% | 58M | ✅ 低波动币（ATR 仅 0.27%），一次异动就是 8 倍 ATR —— 典型插针货 |
| ORDIUSDT | 2.54 | 1.33% | **7M** | ✅ 成交额不足 1000 万，流动性差 |
| BTCUSDT | **3.52** | 0.67% | 18370M | ⚠️ 仅超阈值 0.02，属边界情况 |

> BTC 明天波动数据一变就可能重新通过 —— **不为单个币调阈值**，避免过拟合。

## 流量影响

**零增加**。仍然每 5 分钟每币拉一次 100 根 K线，只是周期从 15m 换成 1h（数据量相同）。

## 追加 · 插针阈值放宽 + 「追加保证金」改名

### 1. 插针阈值 3.5 → 4.0

**`backend/quality.py`**

```python
MAX_SPIKE = 4.0       # 原 3.5
```

**为什么改**：插针比 = `4天内单根1hK线最大振幅 ÷ ATR22`，这个指标对**低波动大市值币系统性偏高** —— BTC 的 ATR 只有 0.64%，分母小，比值天然高。实测 BTC 3.70 / ETH 3.48 排在全场 30 个币的第一、第二名，而它们恰恰是流动性最好的两个标的。这在逻辑上是反的。

## 风控页保存的丢失更新隐患 + 复盘报告误判

### 隐患 1：`save()` 提交整个表单，会覆盖别人刚改的参数

> **更正**：本文最初把 11-05 16:55 的 `max_same_side=6` 定性为"事故"，
> 实际是**浩哥本人在风控页上主动改的**。参数变更本身不是 bug。
> 但排查中发现的下面这个写法确实是隐患，修复保留。

`RiskPage.jsx` 的 `save()` 把**整个表单**（`v`）POST 给后端：

```js
await api.setGlobalRisk(v)   // v 包含全部 7 个字段 + daily_target 子对象
```

任何人打开风控页、点一下保存，就会用**页面加载时那份数据**覆盖后端，
把别人刚改的参数回滚。这是典型的"丢失更新（lost update）"。

**修复**：保存时只提交**改过**的字段

```js
const diff = {}
for (const k of Object.keys(v || {})) {
  if (JSON.stringify(v[k]) !== JSON.stringify(orig[k])) diff[k] = v[k]
}
if (!Object.keys(diff).length) { message.info(t('risk.noChange')); return }
await api.setGlobalRisk(diff)
```

**验证**：
- 打开风控页不点保存 → `POST /api/risk/global` 计数 7 → 7（没触发）✅

## 第四轮：部分平仓被误读为"第二笔独立亏损"

第三版修正了前两轮的问题，但又暴露一个新的：

> 「POL 这个币，昨天开的空头仓位今天又止损一笔，剩一笔还在亏 ——
>   同一币种同方向连吃两次亏，说明对 POL 的空头判断系统性偏了，不止是运气。」

**这是错的。** 查库：

```
positions: id=19  POLUSDT short  qty=5989.47  status=open
trades:    t_id=35 pos_id=19 open           qty=11978.94
           t_id=43 pos_id=19 partial_close  qty=5989.47  pnl=-17.05
```

**同一个仓位（pos_id=19）砍了一半**，剩下一半还在持仓。
不是"两笔仓各亏一次"，是**一笔仓的部分止损**。

AI 据此推出「POL 空头判断系统性偏了」—— 一个基于错误前提的**重判断**。

### 根因

`平仓交易` 表里只有"POLUSDT short -17.05U"，和 `当前持仓` 里的 POL 并列出现，
模型无法区分「这是两个仓位」还是「同一仓位的两次动作」。

### 修复

**1. 平仓表加「类型」列**

```
| 时间 | 币种 | 方向 | 盈亏 | 类型 | 平仓原因 | 持仓时长 | 策略 |
| 11-05 16:44 | POLUSDT | short | -17.05U | 部分平仓(减仓) | — | 16h52m | ... |
- 说明：POLUSDT 是部分平仓，砍掉 5989.47，剩余 5989.47，仓位仍在持仓
  （同一仓位，非新增亏损笔数）
```

**2. 检测「成交笔数 ≠ 独立仓位数」并显式提示**

```python
n_pos = len({r["position_id"] for r in closes if r["position_id"] is not None})
if n_pos != len(closes):
    L.append(f"⚠ 涉及 {n_pos} 个独立仓位，但成交 {len(closes)} 笔 —— 差额是部分平仓")
```

**3. 新增「当前生效风控参数」段**

不让模型从变更历史里猜最终值，直接给确定的事实基线：

```
- 并发上限 max_concurrent_coins = 8
- 单边上限 max_same_side = 6
- 每单风险 risk_per_trade_pct = 0.5%
- 日内熔断 daily_loss_halt_pct = 3.0%
- 由此推出：单边 6 单全止损 = 6 × 0.5% = 3.00%（正好等于熔断线）
```

**4. 变更记录不再全文铺开**

原本 6 条完整消息会让模型数"改了 6 次"并当结论。改为：截断长消息、
标注最早变更时间、明确写「不要数变更条数当分析结论」。

### 一个连带 bug

首次实现时算出「剩余 0.00」—— 因为 `positions.qty` 在部分平仓后
**已被更新为剩余量**，我又减了一次。已修。

### 四轮迭代的总结

| 轮次 | 发现的问题 | 类型 |
|---|---|---|
| 1 | 把改配置前的拦截数据当改配置后的效果 | 时间维度混淆 |
| 2 | 现止损距离当开仓止损距离；杠杆算错 9 倍 | 概念混淆 + 自行估算 |
| 3 | 部分平仓当独立亏损；数变更次数 | 数据关系缺失 |

**三轮全是同一类问题的不同表现：数据没把"关系"和"口径"讲清楚，
模型就用最省事的假设填了空白。**

**结论：给 AI 做数据分析，不能只给数值，必须同时给「这些数值之间是什么关系」。**

## Q3 数据接入：被拦信号的事后验证

浩哥 11-05 批准「加」。新建 `scripts/blocked_outcome.py`（约 210 行）。

### 为什么必须做

Q3「监控池 30 该不该扩」光看拦截次数永远答不了 —— 拦得多不等于拦得错。
必须知道**被拦下的信号后来涨了还是跌了**。

3. 算 24h 净涨跌（按信号方向调整）+ 期间最大有利/不利偏移

**流量**：11-04 实测 56 个币组 → 57 次请求。估算 150–200 KB/天，
比 mark_all 的 69MB/天小两个数量级。

**没有新建 cron** —— 回填挂在 `quant_daily_review.py` 转发器最前面，
失败也不阻塞主报告。避免为了一个回填多养一个定时任务。

### 首跑结果（11-04 数据，已验证）

| 拦截原因 | 条数 | 若开了会赚的比例 | 平均收益 |
|---|---|---|---|
| 并发币数已达上限 | 742 | 50% | +0.04% |
| 杂讯过滤:易插针 | 39 | **72%** | **+1.96%** |
| 杂讯过滤:量小 | 23 | **100%** | **+1.67%** |
| 杂讯过滤:易插针,死水 | 21 | **100%** | +0.72% |
| 空头方向已达上限(4) | 10 | **0%** | **−4.23%** |

**三个发现：**

1. **杂讯过滤确实在漏机会** —— 易插针/量小拦下的信号，72%–100% 会赚钱，

2. **空头方向上限拦得极准** —— 10 条被拦的空头信号，0% 会赚，平均 −4.23%。

### 1. Q8 写进 `docs/优化路线_观察期.md`

+ 仍站 ZLSMA 同侧」。一周 ≥5 次值得做，1-2 次则优先级降到最低。

### 2. 顺手抓到一个静默算错的坑（比 Q8 更严重）

做 Q8 时先写了个探针，算出「POL 空单浮盈 +573.5U」 —— 实际是 −17.8U。

**根因**：`factors.mark_price_of()` 有两级数据源：

```python
live = ws.live_price(symbol)                          # 服务没跑就 None
snap = db.get_factor("mark_all", "", max_age_sec=120)  # 超过 120 秒过期
return (snap.get(symbol) or {}).get("mark", 0.0)       # ← 静默返回 0
```

**取不到价格时返回 0，不抛错、不告警。** 空单用 0 当现价，
`(0.0958 - 0) × 5989 = +573U` —— 一个看起来像巨额盈利的鬼数。

**影响面**：日报所有浮盈亏、名义杠杆、方向分布、Q1 同向浮亏、Q6 板块合计，
全都建在这个价格上。如果日报恰好跑在 mark_all 过期的那两分钟，**整张表静默全错**。

今天没出事只是因为服务一直在跑、快照一直新鲜 —— 纯属运气。

**修复**：日报脚本增加一次实时预取：

```python
def _prefetch_prices(symbols):
    # GET /fapi/v1/premiumIndex（不带 symbol 参数 = 一次拿全部）
    # 只取持仓涉及的币，写入模块级 _PX_CACHE

def _price(sym):
    return _PX_CACHE.get(sym) or factors.mark_price_of(sym) or 0
```

一次请求拿全部币的标记价，流量可忽略。持仓表 / Q1 / Q6 / Q8 统一走 `_price()`。

**教训**：静默返回 0 的函数比抛异常的函数危险得多 —— 抛异常你会知道，
返回 0 你会拿着错数据写出一份看起来很正常、很确定的报告。

74 分钟在目标线上方，确实早该触发。当时 `sustain_sec` 的值因状态被次日覆盖
已不可考，但按默认 300 秒（5 分钟）+ tick 10 秒，用户感知的「半天」就是 5-10 分钟。

「在 180U 被全平」完全符合代码：`sustain_sec=1` + `auto_close_sec=1` =
达标后 2 秒内强制全平，价格从 200 滑到 180 的过程中被砍。

「之后不再进仓」也是设计：`done` 状态 → `blocked()` 拦掉当天所有开仓。

### 发现的设计缺陷

原 `reset()` 只清状态、不清「今日跳过」标记：

```python
def reset():
    for k in ("state","hit_ts","alert_ts","day","pnl_at_alert"): _s(k, "")
```

清完下一轮 tick，若净值仍 ≥ 目标 → 立刻重新 `armed` → 再全平一次。
**用户点重置等于被平第二遍**，所以看起来「按钮没用」。

### 改动

**1. `reset(skip_today: bool = True)`**

- `True`（默认，对应「今日重置」）：清状态 + 记 `skip_day = today` + 解除封锁
- `False`：只清状态，达标会重新触发
- 新增 `skipped_today()`；`tick()` 开头判断今天跳过就 `return`
- 换天 / 关闭开关时调 `reset(skip_today=False)`，避免误设标记

**2. `POST /api/daily-target/reset` 接受 `{"skip_today": bool}`**，返回 `skipped_today`

**3. `summary()` 增加 `skipped_today` 字段**

**4. 前端两个按钮**

- 「今日重置（今天不再自动触发）」→ `skip_today: true`
- 「重新启用今日目标」→ `skip_today: false`
- 点完以后 `dtRefresh()` 立刻刷新（否则页面还显示旧状态）
- 有跳过时显示橙色 `● 今日已重置`

**5. 参数改名成大白话**

| 原名 | 新名 |
|---|---|
| 持续确认 (秒) | 达标要顶住多久才提醒 (秒) |
| 超时自动全平 (秒, 0=不自动) | 提醒后多久强制砍仓 (秒, 0=只提醒不砍) |

**6. 危险提示**：`auto_close_sec ∈ (0, 5]` 时页面顶部红条警告

**7. 踩到的坑：`/api/risk` 不含 `daily_target`**

我给 `const dt = data?.daily_target` 取错了数据源 —— `/api/risk` 只返回
`{global, equity, strategies}`，`daily_target` 在 `/api/status` 里。
结果「今日已重置」标记永远不显示。改为 `GlobalRisk` 内部 `usePoll('/api/status', 5000)`。

### 验证（真机跑过）

| 测试 | 结果 |
|---|---|
| 浮盈 +250U + 今日已重置 → 连跑 10 轮 tick | `state=idle`、`blocked=False`，一次没触发 ✅ |
| 浮盈 +250U + 重新启用 → 跑 1 轮 tick | `state=armed`，正确捕获 ✅ |
| 浏览器点【今日重置】 | 出现 `● 今日已重置：日目标今天不会再自动触发` ✅ |
| 浏览器点【重新启用】 | 标记消失 ✅ |
| 危险提示（auto_close=5） | 页面显示红色警告条 ✅ |

测试后已把状态恢复成 `skipped_today=false`（浩哥今天没要求跳过）。

### 教训

**「重置」这个动作必须定义清楚重置到什么程度** ——
只清状态会立刻重新触发，清状态 + 标记跳过才是用户要的「今天别管我了」。
按钮文案要把这个区别写出来，不能让用户去猜。

### 实测结果（浏览器，非推测）
- 纸面模式：`data-theme=paper`、`bodyBg=rgb(238,237,232)`、canvas 数量 **1**
- 玫红模式：`data-theme=null`、`bodyBg=rgb(5,7,10)`、canvas 数量 **0**（动态层完全卸载）
- 刷新后保持上次选择（`localStorage` 生效）
- 页签粉色残留已清除（React 会把 `#ec4fae` 渲染成 `rgb(236, 79, 174)`，属性选择器补了这条）

### 两个真踩到的坑（留给以后）
1. **颜色不是写在 CSS 里，是写死在内联样式里**。`App.jsx:40` 的 `<b style={{color:'#ff7fcb'}}>` 用类选择器改不动，
   必须用 `[style*="..."]` 属性选择器 + `!important`（外部样式表的 `!important` 能压内联，前提是内联自己没加 `!important`）。
   全站约有 150 处这类硬编码色（`#ff7fcb` 11 处、`#45e6f5` 27 处、`#1b0613` 14 处、红绿 32 处）。
   **这也是为什么没法"整套换浅色"** —— 要一间一间改。
2. **动效一开始画在卡片底下，等于白画**。第一版圆心 `(0.22w, 0.34h)`、半径 315px，
   弧线全落在中间那块深色卡片范围内被盖住；而且墨色 `rgb(21,21,21)` 和卡片底色 `rgb(32,36,42)` 几乎同色。
   修法：① 圆心移到左右边缘 `±0.985w`，弧带贴边；② 颜色改冷白 `rgb(150,185,210)`，深色卡片上才发亮；
   ③ `z-index` 从 1 提到 **9996**（高于内容、低于扫描线 9997）。

### 已知限制
页面留白只有 24px（`padding: 24`），纸白区域约占屏幕 **36%**、深色卡片占 **62%**。
所以动效主要出现在卡片之间的缝隙和边缘，不是满屏流动 —— 这是 A 方案的固有结果，不是 bug。
若想动效更明显，下一步可以把页面 padding 加大或给卡片加圆角留白，但那属于 B 方案范围。

### 补充修复：底部「浮动盈亏」区色差（浩哥 18:51 指出）

**现象**：纸面模式下，底部「浮动盈亏 / 今日已实现」那块看着像个浮起来的白色框，和周边底色不一样。

**根因（实测，不是猜）**：
```
body   = rgb(238, 237, 232)   #eeede8   ← 页面纸底
.stage = rgb(233, 232, 226)   #e9e8e2   ← 底部插画/数据区
```
只差 **5 个色阶**。深色主题下人类眼睛看不出来，纸白背景下就成了一个明显的矩形边界。

**修法**：`.stage` 背景统一为 `#eeede8`（和 body 完全一致），只保留 1px 边框 `#d8d6cf` 划分区域；`.stats` / `.stats-big3` / `.sbig` 全部 `transparent`。同时把底部标签色 `#7f8598`→`#55544f`、`#6b7183`→`#6f6e68`（原色在白底上偏淡）。

**验证**：浏览器实测 `stageBg = bodyBg = rgb(238,237,232)`，截图目视无色差框。

**教训**：深色主题里"几乎看不见"的色阶差，在浅色主题下会放大成明显的边界。换肤时必须**逐个容器核对实际计算色**，不能只换主变量。

### 补充修复：底部五项状态栏对比度（浩哥 18:55 指出）

**现象**：「资金使用率 / 可用保证金 / 持仓数 / 最近爆仓距离 / 平均持仓」这几个数字在纸面上看不清。

**实测对比度（背景 #eeede8，WCAG AA 要求 4.5:1）**：

| 元素 | 原色 | 对比度 | 判定 |
|---|---|---|---|
| 数值 `.val.plain` | `#c8cddd` | **1.35:1** | ❌ 远低于最低要求，等于隐形 |
| 标签 `.lb` | `#6b7183` | 4.15:1 | ⚠️ 刚好卡线（且字号仅 9.5px） |
| 进度条槽 `.bar-line` | `rgba(255,255,255,.08)` | — | ❌ 白底上完全消失 |

**修法**：
- 数值 `#c8cddd` → `#151515`（**15.58:1，AAA**）
- 标签 `#6b7183` → `#4a4a45`（**7.60:1，AAA**），字号 9.5px → 11px，字重 700→800
- 进度条槽 → `rgba(21,21,21,.12)`，填充 → `#151515`
- 净值大数字 `#45e6f5` → `#1d5c6e`（6.38:1）
- 五项上方玫红渐变分隔线 → 墨黑渐变

**验证**：浏览器实测五个 `.ssm` 的 `valColor` 全部为 `rgb(21,21,21)`，`lbColor` 为 `rgb(74,74,69)`；截图目视清晰。

**教训**：深色主题的灵魂是"低对比度高级感"——大量 1.3:1、4:1 的灰字在黑底上显得有层次，换到白底上直接失效。
换肤必须**用 WCAG 公式逐项核算**，不能凭目视。核算脚本已写入本次记录，可直接复用。

## 全量色值体检（2026-11-05 19:05，浩哥批准）

浩哥原话：「把整个 dashboard 页从头到尾走一遍，把所有容器实际计算色抓出来列个表，一次性把不一致的都拉平」

**方法**：浏览器 `getComputedStyle` 逐元素抓实际计算色 + WCAG 2.1 相对亮度公式核算对比度，**不靠目视**。

**体检前后**：

| 指标 | 前 | 后 |
|---|---|---|
| 玫红元素（总览页） | 10 | **0** |
| 低对比度文字（总览页） | **315** | **0** |
| 玫红元素（6 页合计） | 11 | **0** |
| 低对比度（6 页合计） | 318 | **0** |
| 四边边框/渐变/阴影粉色 | 未测 | **0** |

**关键发现**：315 处里 **313 处是同一类东西** —— antd 的 `<Tag>` 组件
（`.ant-tag-green` 279 个 3.37:1、`.ant-tag-cyan` 26 个 3.39:1、`.ant-tag-gold` 8 个 2.76:1）。
antd 预设色是给纯白底调的，纸白 `#eeede8` 上刚好差一口气。深色模式下是实心亮块看不出来，浅色下变成"浅底亮字"直接失效。

**修法**：15 个 Tag 变体全部改为「深色字 + 10% 同色系淡底 + 35% 同色系边框」，变成实心小标签。

**刻意保留的 4 处深色块**（非 bug）：
`.logo` / `.clock` / `.ticker` / `.ant-tabs-ink-bar` —— 都是 `#151515` 墨黑，
设计语言是「纸白底 + 墨黑标注块」，不是"全部变浅"。

**产出**：
- `docs/纸面主题_色值体检报告.md` —— 完整色值映射表 + 踩坑记录
- `preview/audit_theme.js` —— 可复用的体检脚本（以后新增页面跑一遍自查）

**踩坑**：
1. 深色主题的"高级灰"（1.35:1、4:1）在浅色主题下全部失效
2. CSS 类选择器优先级高于全局伪元素，滚动条必须逐个点名
3. antd 的 `darkAlgorithm` 是 JS 层算的 CSS 变量，纯 CSS 改不动
4. 同一视觉层在不同主题下需要不同色阶（body/stage 差 5 阶，深色是层次、浅色是补丁）
5. `vision_analyze` 会把深红 `#c4182c` 认成玫红，色值结论一律以机械判定为准
