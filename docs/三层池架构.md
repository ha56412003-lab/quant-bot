# 三层池架构

> 2026-11-05 上线。候选池(100) → 监控池(30) → 持仓池(6)。
> 每一层解决一个问题：候选池管"市场上有哪些币值得看"，监控池管"哪些现在能交易"，持仓池管"实际下了哪几单"。

---

## 一、架构总览

```
┌─ 第 1 层：候选池  100 只 ─────────────────────────┐
│  刷新：每天凌晨 3 点（1 次/天）                      │
│  流量：约 2.5 MB/次                                  │
│  数据：exchangeInfo + ticker/24hr + 每个币 30 天日线   │
│  组成：自选合约（白名单，优先级最高）+ 成交额排名补满    │
│  落地：data/candidates.json                          │
└──────────────────────────────────────────────────────┘
                        ↓ 100 只
┌─ 第 2 层：监控池  30 只 ──────────────────────────┐
│  刷新：每 1 小时                                     │
│  流量：约 12.4 MB/天                                 │
│  数据：每个币 100 根 1h K 线                          │
│  规则：三道门（成交额/插针/ATR）+ 按成交额取前 30       │
│  落地：内存（quality.py 的 _cache / _monitor）        │
└──────────────────────────────────────────────────────┘
                        ↓ 30 只
┌─ 第 3 层：持仓池  最多 6 个 ──────────────────────┐
│  刷新：每 2 分钟扫信号（策略自己的节奏）               │
│  规则：7 道风控闸门（并发/方向/总敞口/熔断/日目标等）   │
│  落地：SQLite positions 表                            │
└──────────────────────────────────────────────────────┘
```

## 二、第 1 层：候选池

### 组成规则

```
最终 100 只 = 白名单（无条件进） + 规则筛入（补满剩余位置）
```

### 规则筛入的四道基础门

| 门 | 条件 | 挡什么 |
|---|---|---|
| ① 资产类型 | `underlyingType = COIN` | 排除股票代币（TSLA/NVDA/GOOGL） |
| ② 计价资产 | `quoteAsset = USDT` | 排除 USDC 本位（BTCUSDC 等） |
| ③ 合约类型 | `contractType = PERPETUAL` | 排除季度交割合约 |
| ④ 交易状态 | `status = TRADING` | 排除已下架 |

**为什么必须过滤股票代币**：2026-11-05 实测，成交额 Top 41 里有 **31 个是股票/黄金/指数代币**。不过滤的话候选池会被 TSLA、NVDA、QQQ 这类填满，而它们有美股交易时段限制、股息/拆股调整，跟加密的价格行为完全不同。

币安 `exchangeInfo` 里 `underlyingType` 字段直接标明：
- `COIN` → 真加密货币（703 个）
- `EQUITY` / `KR_EQUITY` / `HK_EQUITY` / `CN_EQUITY` → 股票（222 个）
- `COMMODITY` → 商品（黄金 XAU、白银 XAG，8 个）
- `INDEX` / `FX` / `PREMARKET` → 指数/外汇/盘前（9 个）

### 第五道门：30 天振幅阀门

```
振幅 = (30 天最高价 - 30 天最低价) / 30 天最低价 × 100%
合格区间：[10%, 300%]
```

**这两个数字怎么定的**（2026-11-05 实测 200 个币的 30 天日线）：

| 统计 | 值 |
|---|---|
| 中位数 | 62% |
| P10 | 28.9% |
| P25 | 39.5% |
| P75 | 129.1% |
| P90 | 357.3% |

**下限 10% 的依据**：
- 必须保住 BTC（13.0%）和 BNB（15.1%）—— 它们是前 100 名里振幅最低的两个真币
- 10% 刚好能剔除 PAXG(8.3%)、XAUT(8.7%)、USDC(0.3%) 这些非加密资产和稳定币
- 如果设成 15%，**BTC 会被剔出去** —— 这是绝对不行的

**上限 300% 的依据**，剔除的典型：

| 币 | 振幅 | 30 天涨跌 | 问题 |
|---|---|---|---|
| AKE | 1745% | **-90.6%** | 崩盘币 |
| AIN | 1061% | +669% | 妖币 |
| Q | 1037% | +29% | 日波动 54%，极端 |
| JCT | 599% | +355% | 拉盘币 |
| AGT | 760% | +12% | 巨幅震荡 |
| UAI | 443% | -62.9% | 崩盘 |

这类币的共同问题：**止损会被一根 K 线直接扫穿**。ATR 巨大导致仓位算出来极小（几十 U），赚不到钱但一旦被扫就是满额亏损。

**实测效果**：前 100 名里 88 个通过，前 200 名里 183 个通过 —— 凑满 100 无压力。

### 白名单（自选合约）

| 项 | 规则 |
|---|---|
| 在哪配 | 配置页 →「每天候选币池」→「自选合约」输入框 |
| 优先级 | **最高**，先占位，规则筛入只补剩余名额 |
| 是否过振幅阀门 | **不过**。但你塞进去的币还得过监控池的三道门才能真的交易 |
| 是否会失效 | 如果该币已下架/不在 `TRADING`，会自动跳过并在界面提示 |

### 每日重建流程

```
1. GET /fapi/v1/exchangeInfo        1145 KB  → 挑出 519 个真币 USDT 永续
2. GET /fapi/v1/ticker/24hr          291 KB  → 拿到每个币的 24h 成交额
3. 白名单先占位
4. 按成交额降序扫描，逐个 GET /fapi/v1/klines?interval=1d&limit=31  (~4 KB/币)
5. 过振幅阀门的收入，直到凑满 100
6. 写 data/candidates.json
```

实测：扫描 111 个就凑满 100，耗时 **12.7 秒**。

## 三、第 2 层：监控池

### 三道门（原有的，未改）

| 门 | 阈值 | 挡什么 |
|---|---|---|
| ① 成交额 | 24h < **1000 万 U** | 流动性差，滑点吃人 |
| ② 插针比 | 单根最大振幅 ÷ ATR > **4.0** | 止损被一根针扫掉 |
| ③ 死水 | ATR ÷ 价格 < **0.6%** | 波动太小，止损窄到没意义 |

数据源：每个币 **100 根 1h K 线**（96 根 = 4 天窗口）。

### 新增：席位竞争

```
候选池 100 只 → 过三道门 → 通过的按「24h 成交额」降序 → 取前 30 名进监控池
```

**为什么要排序**：100 只里可能有 60~88 个都过门，但监控池只有 30 个席位。按成交额排序最直观 —— 流动性好 = 滑点小 = 能拿到策略算出来的价格。

实测（2026-11-05）：100 只里 **88 个过门**，抢 30 个席位，第 31 名 ARB（0.74 亿）开始落选。

### 刷新频率：5 分钟 → 1 小时

**为什么改**：
- 插针/ATR 是用 **1h K 线**算的，5 分钟刷一次等于同一根 K 线重复算 12 遍，纯浪费
- 1 小时刷新正好跟 K 线粒度对齐

**流量反而更省**：

| 方案 | 请求/天 | 流量/天 |
|---|---|---|
| 改前 30 币 × 5 分钟 | 8640 | 44.7 MB |
| 改后 100 币 × 1 小时 | 2400 | **12.4 MB** |
| 对比 | | **省 72%** |

## 四、第 3 层：持仓池

**完全没改**。策略扫描仍是每 2 分钟，7 道风控闸门全部保留：

1. 日内熔断（当天亏 3% → 停到次日 UTC 0 点）
2. 日目标已达（赚够 200U → 今日停止开新仓）
3. 事件静默（高重要性经济事件前 30 分钟不开仓）
4. 同币已有仓位（禁止对锁/加仓）
5. 并发币数 ≤ 6
6. 单方向 ≤ 4（多空各最多 4 个）
7. 总敞口 ≤ 余额 × 3

## 五、池与池的边界（重要）

### 核心原则

> **池子管的是「能不能开新仓」，不管「已经开的仓」。**

| 情况 | 怎么处理 |
|---|---|
| 持仓中的币，掉出监控池 | **不影响**。止损/止盈/信号照常运行 |
| 持仓中的币，掉出候选池 | **不影响**。同上 |
| 监控池的币，掉出候选池 | 下次监控池刷新（1 小时）时移出 |
| 白名单的币被删除 | 下次重建/刷新时移出（持仓不动） |

### 技术保证

`quality.is_tradable()` 在整个代码库里**只在 `engine.py:166` 被调用一次**，位置是信号评估阶段（准备开新仓）。持仓管理循环 `position_loop` 完全不经过它。

**实测验证**（2026-11-05）：6 个持仓里 ATOM / TIA / POL / ARB 都没进监控池（成交额掉到 0.18~0.74 亿），但它们的管理完全正常。

## 六、参数在哪改

全部集中在 `strategies.yaml` 的 `pools` 段：

```yaml
pools:
  candidate:              # 第 1 层
    size: 100             # 候选池目标数量
    refresh_hour: 3       # 每天几点重建
    min_amp_pct: 10.0     # 30 天振幅下限
    max_amp_pct: 300.0    # 30 天振幅上限
    vol_days: 30
    whitelist:            # 自选合约
      - BTCUSDT
      - ETHUSDT

  monitor:                # 第 2 层
    size: 30              # 监控池席位
    refresh_sec: 3600     # 刷新间隔（秒）
    min_quote_vol: 10000000
    max_spike: 4.0
    min_atr_pct: 0.6

  position:               # 第 3 层
    max_concurrent: 6
    scan_interval: 2m
```

**改完不用重启**：`config.pools()` 每次刷新时重新读，`quality.configure()` 会热更新阈值。

只有 `candidate` 段的部分参数（size / refresh_hour / 振幅 / vol_days）在**启动时**读取 —— 改了要重启，或者点「立即重建候选池」。

## 九、故障排查

| 现象 | 原因 | 怎么修 |
|---|---|---|
| 候选池 0 只 | `data/candidates.json` 不存在且重建失败 | 配置页点「立即重建候选池」，看错误提示 |
| 监控池 0 只 | 刚启动还没跑完第一轮（约 20 秒） | 等 30 秒 |
| 监控池一直 0 | 候选池为空，或三道门全部不过 | 查 `/api/pool` 的 `pass_n` |
| 白名单币没进池 | 该币不在币安 `TRADING` 状态 | 配置页会显示「已跳过」提示 |
| 某币明明成交额很高却不在监控池 | 过了三道门但没抢到前 30 席位 | 看「池」列显示的是「候选」而不是「监控」 |

## 十一、流量总账（2026-11-05 体检后修正）

**这里记一个血泪教训**：三层池上线后，候选池从 30 只扩到 100 只，
`ws.py` 的 `@bookTicker` 订阅也跟着从 30 变 100 —— 那是**逐笔推送**，
实测 **21.7 GB/天**。这跟"一晚上跑几十个 G 流量"的事故完全对得上。

**根因**：扩池的时候只想着"币多了要都盯上"，没算订阅的流量账。

**现在各数据源的真实成本**：

| 项目 | 频率 | 流量/天 | 说明 |
|---|---|---|---|
| `mark_all`（premiumIndex 全市场） | 30 秒 | 69 MB | 候选池 100 个币的价格都从这里来 |
| 持仓币价格（REST 单币 × 6） | 5 秒 | 7.3 MB | 只为止损止盈的及时性 |
| 监控池 K 线（100 币 × 100 根 1h） | 1 小时 | 12.4 MB | 三道门判定 |
| 候选池每日构建 | 1 天 | 2.5 MB | exchangeInfo + ticker + 日线 |
| 信号扫描 K 线（S15 每 2 分钟） | 2 分钟 | ~84 MB | 策略评估 |
| **合计** | | **约 175 MB/天** | |

**如果以后要加数据源，先算三件事**：
1. 单次请求多大（用 gzip 后的大小）
2. 一天多少次
3. 乘起来是不是超出 200 MB/天这个心理线

**WS 为什么不用了**：币安 `@bookTicker` 是逐笔推送，BTC 一个币就 3.2 GB/天。
除非策略真的需要 tick 级数据（目前只有关闭状态的 S11 需要），否则用 REST 轮询。
