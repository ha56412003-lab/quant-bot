## 这是什么

一句话：**从全市场 500+ 个合约里，每天筛出 200 个值得看的，再滚动缩到 69 个可交易的，最后同时持有不超过 6 个仓位。**

它不做的事（避免误解）：

| 不做 | 原因 |
|---|---|
| ❌ 不预测价格 | 只用趋势状态 + K 线形态判断「现在该不该跟」 |
| ❌ 不做高频 | 最短周期 15 分钟 K 线，不是秒级套利 |
| ❌ 不做网格/马丁 | 只用固定风险 + 止损，不加仓不摊平 |
| ❌ 不做主观判断 | 全部规则化，情绪不参与 |

它做的事：

| 做 | 说明 |
|---|---|
| ✅ 多币种分散 | 单笔风险 1.5%（1R ≈ 150U），最多 6 个仓位分散，单币爆仓不影响整体 |
| ✅ 严格止损 | 每单开仓就带止损，取 20 根阶段低点，不靠感觉 |
| ✅ 让利润奔跑 | 到 2R 只平一半，剩一半跟着趋势跑到破均线 |
| ✅ 自动缩量 | 市场极端贪婪/恐惧时自动减仓 |
| ✅ 数据可追溯 | 每笔交易记录开平仓时的因子快照，事后能复盘 |

## 核心设计：三模块分工

系统拆成三块，各管各的，**互不越界**。这是整个项目最重要的设计约束。

| 模块 | 管什么 | 边界 |
|---|---|---|
| **① 池子模块** | **资格** —— 这个币现在能不能做 | 只管把「值得看的币」送到策略面前，**不判断买卖点** |
| **② 买卖模块** | **时机** —— 此刻该不该开仓、什么时候出 | 只判断信号，**不管仓位大小** |
| **③ 风控模块** | 仓位大小、单笔亏损、熔断、并发上限 | **全局唯一**，谁都不许绕开 |

**为什么要这样拆**：如果让策略自己决定「买多少」，不同策略就会用不同的风险逻辑，出了事无法归因。
现在无论加多少个策略，风控永远是同一套账。

**三条不许越界的线**：

- 池子模块 ❌ 不算 CE / HA / BBW / 止损止盈 / 仓位
- 买卖模块 ❌ 不管池子怎么选币 / 不管仓位大小
- 风控模块 ❌ 不判断信号好坏，只算「这笔能不能开、开多大」

```

└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  筛选层（三层池）                                              │
│  候选池 200 ──每天3:00──▶ 监控池 ≤23 ──风控──▶ 执行层 ≤8      │
└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  策略层                                                       │

└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  风控层（8 道闸）                                              │
│  熔断 → 日目标 → 事件静默 → 同币去重 → 并发上限 → 方向上限     │
│  → 杠杆上限 → 策略额度 → 仓位计算                              │
└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  执行层                                                       │
│  paper 模拟（默认） / 实盘（币安·Bitget·OKX）                  │
└───────────────────────────┬──────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  记录层                                                       │
│  SQLite（仓位/成交/信号/权益曲线） + JSONL（交易日志）         │
└──────────────────────────────────────────────────────────────┘
```

**两个独立循环，都在跑**：

| 循环 | 频率 | 干什么 |
|---|---|---|
| `position_loop` | 0.5 秒 | 管已有仓位：止损/止盈/移动止损/超时出场 |
| `scan_loop` | 0.5 秒 | 拉因子、扫策略、处理信号、开新仓 |

**为什么分开**：持仓管理不能等策略扫描。市价突然砸下来，止损要立刻执行，不能等下一个 2 分钟扫描周期。

## 三层币种池

### 第一层：候选池 200 个

**刷新频率**：每天凌晨 3:00（流动性最低，24h 成交额数据已完整）

**筛选规则**：

| 门 | 条件 | 为什么 |
|---|---|---|
| ① | `underlyingType = COIN` | 排除 TSLA/NVDA 等股票代币 |
| ② | `quoteAsset = USDT` | 排除 USDC 本位（流动性差） |
| ③ | `contractType = PERPETUAL` | 排除季度交割（会到期） |
| ④ | `status = TRADING` | 排除已下架 |
| ⑤ | 30 天振幅 ∈ **[10%, 300%]** | 太死不赚钱，太疯止损被扫 |

**振幅阀门的来由**（2026-11-05 实测 200 个币）：

```
中位振幅 62%，P10 = 28.9%，P90 = 357%

下限 10%：剔除 PAXG(8.3%)/XAUT(8.7%)/USDC(0.3%) 这类非加密资产和稳定币
         同时保住 BTC(13.0%)、BNB(15.1%) —— 前 100 名里振幅最低的真币
上限 300%：剔除 AKE(1745%, 30天-90.6%)、Q(1037%)、AIN(1061%, +669%) 这类妖币
         它们的止损会被一根 K 线直接扫掉
```

**排序**：按 24 小时成交额降序，白名单币种优先占位。

**流量成本**：约 4 MB/天。

---

### 第二层：监控池 ≤ 69 个

**刷新频率**：池内币 **3 分钟** / 池外币 **15 分钟** / 日线指标 **每天**（分级刷新控流量）

**三道门**：

| 门 | 条件 | 阈值来由 |
|---|---|---|
| ① 24h 成交额 | ≥ **1000 万 U** | 低于此值的币滑点能吃光利润 |
| ② 插针比（**日线**） | ≤ **4.0** | 单根 K 线振幅 / ATR，超过说明止损容易被扫 |
| ③ **ATR 准入门槛**（**5 分钟**） | **> 1.20%** 才进池 | 只收高波动币。进池满 30 分钟若没被选进持仓池且 ATR 掉到 0.80% 以下，清退 |

**插针比为什么要用日线而不是 15 分钟算**：

> 15m K 线噪音太大——每根都可能是十字星，29 个币的 max振幅/ATR 全落在 4~8.4，
> 导致 28/30 个币被判"易插针"，监控池实际只剩 1 个币可用。
> 改用**日线**（30 根 = 30 天窗口）后，噪音被平滑，区分度正常。

**插针比为什么从 3.5 放宽到 4.0**：

> 插针比 = 最大单根振幅 / ATR，对低波动大市值币系统性偏高。
> BTC 的 ATR 只有 0.64%，分母小 → 比值天然高，实测 3.70 被误判；ETH 3.48 擦边。
> 放宽到 4.0 后 BTC 放行，TRX(8.53) 等真正易插针的币仍被拦。

**容量**：上限 **69**（2026-11-06 晚从 23 放开），两档交替补位，**不设硬配额**。

> **为什么从 23 放到 69**：实测 `pass_n=69`（通过全部门槛的币）但 `monitor_n=22` ——
> 47 个合格币被容量挡在外面，系统根本不扫。单独扫这 47 个发现有 **4 个正在 CE 翻转**
> （INIT / LIT / FLUID / FOGO），机会被白白扔掉。
> 代价：池内 3 分钟刷新从 22 个涨到 69 个，流量约 63 → 105 MB/天（+41MB，月 +1.2GB），
> 请求数 10,560 → 33,120 次/天（并发 8 + 0.03s 错峰，币安权重安全）。

**⚠️ 重要**：**持仓中的币不受池子进出影响**。池子只管「能不能开新仓」，不管平仓。
一个币被踢出监控池后，如果还有仓位，会继续正常管理到平仓为止。

### 第三层：执行层（最多 6 个）

受风控层的并发上限约束，见[风控体系](#风控体系)。

> **术语说明**：这一层严格来说不是「池」，而是**实际持有的仓位**。早期文档叫「持仓池」，容易和「池子」混淆，现已正名为**执行层**。

**为什么要三层**：

如果直接对全市场 500 个币跑策略，会有两个问题：
1. **算力/流量爆炸**——每 2 分钟算 500 个币的指标，网络和 CPU 都扛不住
2. **信号淹没**——垃圾币的假信号会挤占真实机会

三层池是**漏斗**：先用便宜的条件粗筛（振幅），再用较贵的条件细筛（ATR/插针），最后才跑策略。

## S15 策略详解

### 名字含义

**S15 = Heikin Ashi + Chandelier Exit（吊灯止损）+ ZLSMA（零滞后均线）**

三个部件都跑在 **Heikin Ashi（平均K线）** 上 —— 这是浩哥在 TradingView 图上
实际看到的组合，参数为 **CE(ATR周期 1 × 倍数 2.0) + ZLSMA 50**。

> **为什么必须用 HA**：指标输入是 HA 的收盘价，不是原始收盘价。用原始 K 线
> 算出来的买卖点和他在图上看到的箭头对不上 —— 这是早期最坑的一个偏差。

### 组件一：Chandelier Exit

**作用**：判断「现在是多头趋势还是空头趋势」

**公式**（everget 原版）：

```python
atr = ce_mult × ATR(ce_len)

# 多头止损线（吊灯从上往下吊）
longRaw = highestHigh(ce_len) - atr
# 空头止损线
shortRaw = lowestLow(ce_len) + atr

# 棘轮机制：只朝有利方向移动，不回头
longStop  = close[1] > longStop_prev  ? max(longRaw,  longStop_prev)  : longRaw
shortStop = close[1] < shortStop_prev ? min(shortRaw, shortStop_prev) : shortRaw

# 状态机：收盘价在两条线之间的哪一边
dir = close > shortStop_prev ? 1 : (close < longStop_prev ? -1 : dir_prev)
# dir = 1 多头，dir = -1 空头
```

**核心是「棘轮」**：多头止损线只会往上移，不会往下退。这样趋势走得越远，保护利润的线就跟得越紧。

当前参数 `ce_len = 1`、`ce_mult = 2.0`。

### 组件二：ZLSMA（零滞后 SMA）

**作用**：判断「K 线有没有真的站上去」

**公式**：

```python
lsma1 = linreg(close, z_len, 0)      # 对收盘价做线性回归估值
lsma2 = linreg(lsma1, z_len, 0)      # 再对结果做一次
zlsma = lsma1 + (lsma1 - lsma2)      # 补上滞后量 = 零滞后
```

普通移动平均的问题是**滞后**：均线总是慢半拍，等它转向，行情已经走了一半。
ZLSMA 用「回归值 + 回归差值」抵消滞后，让均线更贴近当前价格。

> **⚠ 一个踩过的坑**：第二次线性回归的输入里含 `None`（前 `z_len` 根还没值）。
> 如果把 `None` 当 0.0 参与求和，ZLSMA 会被算成价格的两倍 —— 实测某币
> 真值 0.2604、错误值 0.4802。正确做法是「窗口内只要有一个 None，本根就返回 None」。
> 这个 bug 曾让两份回测脚本跑出 13R 的差异。

### 入场规则

**五个条件全部满足才开仓**：

```
① CE 方向翻转 —— 本根 dir ≠ 上一根 dir（这是「事件」，不是「状态」）
② 关键 K 线 —— HA 阳线且收盘 > ZLSMA（做多）/ 阴线且收盘 < ZLSMA（做空）
③ 池子资格 —— 5m ATR > 1.20% 且 成交额 ≥ 1,000 万 U 且 插针 ≤ 4.0（见池子章节）
④ 震荡过滤 —— 布林带宽度(20,2) 在过去 100 根中的分位 > 70%
⑤ 当前没有该币仓位
```

**���键细节**：所有判断用最后一根**已收完**的 K 线（`len(ks) - 2`）。绝不用未收盘的当前 K 线 —— 否则信号会闪烁、会重绘、回测会虚高。

#### 为什么 CE 翻转必须是「事件」而不是「状态」

早期实现是「只要 dir == 1 就出信号」，结果一根 K 线刷一次，信号数量是正确
实现的 7 倍。TradingView 上的箭头是**翻转那一刻**画的，不是每根都画。

#### 为什么 ATR 门槛是生死线

止损距离决定手续费占 R 的比例：

```
每笔费用(R) = 0.0013 ÷ 止损距离
盈亏平衡的止损距离 = 4.28%
```

ATR 2.5% 时止损距离中位约 2%，费用占 0.05R，是毛利 0.019R 的 2.6 倍 —— **数学上必亏**。
ATR > 2.5% 把止损距离中位推到 7.57%，费用降到 0.017R，才活得下来。

#### 为什么用布林带宽度而不是 ADX

三个候选过滤器都实测过（15m / 120 天 / 14 个高波动币）：

| 过滤器 | 净总 R | 结论 |
|---|---|---|
| **布林带宽度分位 > 70%** | **−0.88** | ✅ 唯一有效的 |
| 不过滤 | −37.56 | ❌ |
| ADX > 25 | 更差 | ❌ 滞后 |
| ADX 上升 3 根 | −5.54 | ❌ 滞后 |
| Kaufman 效率比 ER20 > 0.25 | −30.20 | ❌ 滞后 |

ADX 和效率比的共同毛病是**滞后**：等它们确认「趋势来了」，趋势已经走完，
进场就是追高。布林带宽度衡量的是「价格分散程度」，没有这个问题。

### 出场规则

**四条同时生效，谁先满足谁动**：

| 出场方式 | 条件 | 动作 |
|---|---|---|
| **① 止损** | 价格触及 `stop_price` = 20 根阶段低点（多头取最低、空头取最高） | 全平 |
| **② 到 2R 平一半** | 浮盈达到 **2.0R**（`half_at_r`）且还没平过一半 | **平掉 50%，剩一半继续持有** |
| **③ 趋势反转出场** | 收盘破 ZLSMA **且**从持仓期最高浮盈回撤 ≥ 0.8R，**连续 2 根确认** | 全平 |
| **④ 时间止损** | 持仓满 **16 小时**且没到过 2R | 全平（**已平过一半的仓位豁免**） |

**为什么②是「平一半」而不是「全平」**：原规则是「赚到 1.2R 整仓全平」，
把最大单笔盈利锁死在 +1.19R —— 那不是趋势跟踪，是小波段收割。
改成「2R 平一半、剩一半交给③管」后，利润能跟着趋势跑完。

**为什么④对已平一半的仓位豁免**：回测口径是「没到 2R 才按时间撤」，
实盘原为无条件平仓。不豁免的话，一笔已经平过一半、正在走趋势的单子
到 16 小时会被砍掉，「让利润奔跑」白做。

#### 止损为什么取阶段低点而不是 ATR 倍数

同规则下对比（2866 组样本）：

| 止损方式 | 净总 R | 被扫止损次数 |
|---|---|---|
| **阶段低点（取远）** | 基准 | — |
| 收窄取近 | **−632.52** | 1960 次 |

取近等于把止损放在「稍微一动就被扫」的位置，被反复收割。

**2026-11-06 又测了「用 ATR 倍数把止损推远」能不能少被扫** —— 不能，反而更糟：

| 止损方式 | 净 R | 止损出场占比 |
|---|---|---|
| **阶段低点（现用）** | **+38.22** | 31.9% |
| 前 50 根阶段低点 | +35.81 | 32.4% |
| 2.0×ATR 兜底 | +32.67 | 32.8% |
| 3.0×ATR 兜底 | +35.44 | 36.8% |
| 4.0×ATR 兜底 | +10.31 | **46.0%** |

止损放宽后「止损出场占比」反而上升、收益腰斩。**31.9% 的止损率是趋势跟踪的正常水平**
（约三分之一的单子止损离场），不是缺陷。

#### 为什么止盈规则从「1.2R 全平」改成「2R 平一半」

三种卖法在 20 币 / 60 天 / 同一批入场信号上的对照（1R = 150U）：

| 方案 | 参数 | 笔数 | 净 R | 胜率 | 盈亏比 | 最大回撤 |
|---|---|---|---|---|---|---|
| 原规则 | 1.2R 全平 | 498 | **−3.08** | 43.0% | 0.98 | −32.1 |
| K | 1.2R 平一半 | 472 | +31.99 | 43.6% | 1.17 | −24.0 |
| **L（现用）** | **2.0R 平一半** | 477 | **+38.22** | 42.1% | 1.20 | −25.8 |
| B | 完全放开止盈 | 478 | +46.99 | 42.3% | 1.24 | −29.2 |

选 2.0R 而不是「完全放开」：B 多赚 8.8R，但回撤深 3.4R，
且 **B 在宽幅震荡上亏 −10.13R，L 只亏 −6.97R** —— L 更抗震荡。

按行情类型拆开（每方案独立分类，用 30 天趋势效率 = |净涨跌| ÷ 总振幅）：

| 行情类型 | 原规则 | 2R 平一半 |
|---|---|---|
| 单边趋势（47 笔） | +9.99 | **+11.00** |
| 半趋势半震荡（115 笔） | +4.63 | **+23.90** |
| 宽幅震荡（129 笔） | −10.84 | **−6.97** |

**利润大头来自「半趋势半震荡」，不是纯单边**；且新规则把震荡亏损从 −10.84 缩到 −6.97。

#### 为什么趋势反转要带「回撤门槛 + 连续确认」

**「价格一穿均线就跑」在震荡市是灾难**。实测：

| 出场规则 | 触发次数 | 手续费吃掉 | 净总 R |
|---|---|---|---|
| 一穿就走 | 4891（占 95%） | 274R | −225 |
| **回撤 ≥ 0.8R 且连续 2 根确认** | 186 | 少 | 正 |

「一穿就走」触发太频繁，手续费是头号杀手。加门槛后逻辑也说得通：
**赚到的利润回吐超过 0.8R 才认输，而不是价格碰到均线就慌。**

> ⚠ 注意术语：「回撤」是**相对持仓期最高浮盈**算的，不是「浮盈不足 X R 就不平」。
> 方向搞反会变成完全相反的规则（这个错误踩过）。

#### 为什么时间止损是 16 小时

回测里平均持仓 **6.93 小时**、中位 **4.50 小时**。设 4 小时 = 从中位数位置把
一半的单子砍断（净 R 从 +21.71 掉到 +5.30）。16 小时只削掉最慢的那一小撮。

**成交成本**：挂单 maker 0.02% + 零滑点，与回测同口径。
（⚠ 这是「假设挂单能成交」的记账口径 —— 引擎当前是市价成交，真实限价挂单能力尚未实现。）

## 价格口径

**一句话：「平均 K 线看路，真实价算钱。」**

| 用途 | 用哪个价 | 为什么 |
|---|---|---|
| 判断方向（多空 / 站没站上均线） | **HA 合成价** | 平滑噪音，看趋势更清楚 |
| 算**入场价** | **真实收盘价** | HA 价实盘根本成交不了 |
| 算**止损** | 真实 K 线的 20 根阶段低点 | 市场结构用真实价衡量 |
| 算**止盈** | 入场价 ± 风险 × 1.2 | — |
| 记录 | 真实成交价，滑点如实记 | — |

> 早期版本用 HA 价当入场价，结果实盘和回测对不上（HA 收盘和真实收盘能差 2% 以上）。
> 现在明确规定：**指标用 HA，钱用真实价。**
>
> 滑点导致的 RR 偏离（比如某单实际 RR 1.83 或 0.73）是如实记录，不是 bug。

## 仓位是怎么算出来的

这是整套系统最核心的数学。**每一笔开仓的数量都由公式算，不由人决定。**

### 公式

```python
# 第一步：这笔交易最多愿意亏多少钱
risk_usd = capital × risk_per_trade_pct / 100 × size_mult

# 第二步：止损距离（开仓价到止损价）
stop_dist = |price - stop_price|

# 第三步：由此反推数量
qty = risk_usd / stop_dist

# 第四步：三重上限，谁小用谁
notional = qty × price
notional = min(notional, max_position_usd)                    # ① 策略单笔上限
notional = min(notional, capital × leverage - used)           # ② 策略剩余额度
notional = min(notional, equity × max_position_pct_per_coin   # ③ 全局单币上限
                       / 100 × leverage)

qty = notional / price
```

### 为什么这么算

**核心思想：固定风险，变动仓位。**

假设：
- 账户权益 10000 U
- 每单风险 1.5% → 最多亏 150 U
- 止损距离 2% → 止损价 = 开仓价 × 0.98

那么：
```
qty = 150 / (price × 0.02)
```

如果 price = 100，则 `qty = 150 / 2 = 75`，名义价值 7500 U。

**关键特性**：波动大的币，止损距离大，自动算出来仓位就小；波动小的币，止损窄，仓位自动变大。

**这样保证每笔交易的「最大亏损金额」都一样**，不会因为某个币波动大就亏得多。

### 具体数字（当前配置）

| 参数 | 值 | 含义 |
|---|---|---|
| `risk_per_trade_pct` | **1.5%** | 每单最多亏权益的 1.5%（1R ≈ 150 U） |
| `max_concurrent_coins` | **6** | 最多同时持有 6 个币 |
| `max_same_side` | **6** | 做多最多 6 个，做空最多 6 个 |
| `max_gross_leverage` | **6** | 总名义价值 ≤ 权益 × 6 |
| `max_position_pct_per_coin` | **32%** | 单币名义价值 ≤ 权益 × 32% × 6 |
| `daily_loss_halt_pct` | **10%** | 当日亏 10% 停开新仓 |
| `daily_target.target_usd` | **800 U** | 当日浮盈到 800 U 落袋收工 |

**以 10000 U 权益计算**：

```
每单最大亏损 = 10000 × 1.5% = 150 U
6 个仓位全部止损 = 900 U 亏损（权益的 9%）
```

**注意 `max_position_pct_per_coin` 是仓位的真正天花板**：
止损 1.6% 时 1.5% 风险需要 9,380U 名义，单币上限 32% × 6x = 19,210U，够用。
但如果这个值仍停在 10%，名义上限只有 3,002U，1.5% 会被截成 0.48% —— **改了白改**。

### 防止除零

`position_qty()` 有三处保护：

```python
if price <= 0:      return 0     # 价格无效
if stop_dist <= 0:  return 0     # 止损距离为 0
if not sig.stop_price:
    stop_dist = price * 0.01     # 策略没给止损，用 1% 兜底
```

## 风控体系

**每一笔开仓要经过 8 道检查，任何一道不过就拒绝。**

顺序很重要——越早拒绝的越便宜。

### 闸门顺序

| # | 闸门 | 条件 | 拒绝原因 |
|---|---|---|---|
| 1 | **日内熔断** | 当日已实现亏损 ≥ **10%** 权益 | "日内熔断中" |
| 2 | **日目标已达成** | 当日浮盈达到目标并已落袋 | "已达日目标，今日停止开新仓" |
| 3 | **事件静默** | 30 分钟内有高重要性经济事件 | "事件静默(非农就业)" |
| 4 | **同币去重** | 该币已有仓位 | "同币已有仓位(禁止对锁/加仓)" |
| 5 | **并发上限** | 持仓币种数 ≥ **6** | "并发币数已达上限" |
| 6 | **方向上限** | 同方向持仓 ≥ **6** | "多头方向已达上限(6)" |
| 7 | **总杠杆** | 总名义价值 / 权益 ≥ **6** | "总敞口已达杠杆上限" |
| 8 | **策略额度** | 该策略已用满分配资金 | "策略分配资金已用满" |

**为什么第 6 道要限制方向**：

> 避免 6 单全空/全多。市场单边反转时，同方向的仓位会同时扫损。

### 额外的仓位调节

**恐惧贪婪指数调节**（`fear_greed_extreme`）：

```
市场极端贪婪（≥ 84）且要做多 → 仓位 × 0.5
市场极端恐惧（≤ 16）且要做空 → 仓位 × 0.5
```

**逻辑**：别人贪婪时你更贪婪，容易被埋在山顶。

### 风控的已知局限

1. **熔断只算已实现亏损**，浮亏不算。持仓浮亏 10% 也不会触发熔断。
2. **6 × 1.5% = 9.0%，熔断线 10%，缓冲只有 1 个点。**
   6 个同向仓位全部止损时亏 9%，刚好卡在熔断线下面 —— 这是故意的：
   一次全扫不至于停摆一天，但当天基本也就收手了。
3. **Event 静默依赖经济日历数据**，数据源缺失时不会静默。
4. **⚠ 全仓模式（cross）** —— OKX 用 `tdMode:"cross"`、Bitget 用 `marginMode:"crossed"`。
   6x 杠杆全仓下 6 个仓位共用保证金池，一个币剧烈插针会吃掉共用保证金、
   连累其他仓位被强平。**接实盘前必须改成逐仓 isolated。**

## 熔断与日目标

### 日内熔断

**触发条件**：当日已实现亏损 ≥ 权益的 3%

**触发后果**：
- 立刻停止开新仓
- 已有仓位继续管理（不止损、不平仓）
- 持续到解除时间后自动恢复

**为什么是 10%**：
```
每单风险 1.5%，最多 6 个仓位
6 × 1.5% = 9.0%

熔断线 = 10%
         ↑ 留 1 个点缓冲
```

**为什么留 1 个点的缓冲**：6 个仓位同时被扫的极端情况亏 9%，如果熔断线也是 9%，
会在「最后一次止损」那一刻正好触发全站停摆 —— 当天等于没交易，但亏的钱已经亏了。
留 1 个点让它能撑完当天，第二天照常开。

> 历史口径：0.5% 时代是 6 × 0.5% = 3.0%，熔断线 3.0%，**零缓冲**。
> 当时就记了这个「已知问题」，这次一并修掉了。

**实现位置**：`backend/risk.py:27-34`，熔断时间写入数据库 `meta.halt_until`。

### 日目标（落袋为安）

**作用**：当天赚够了就收手，不贪。

**四状态机**：

```
idle（等待）
  ↓ 浮盈 ≥ target_usd
armed（已达标，等确认）
  ↓ 连续 sustain_sec 秒保持在目标之上
alerted（已提醒，可自动平仓）
  ↓ auto_close_sec 秒后 / 手动确认
done（今日收工，不再开新仓）
```

**当前参数**：

| 参数 | 值 | 含义 |
|---|---|---|
| `enabled` | true | 启用 |
| `target_usd` | **800** | 目标浮盈 800 U（= 5.33R） |
| `sustain_sec` | 30 | 要连续顶住 30 秒（tick 每 10 秒） |
| `auto_close_sec` | 5 | 达标后 5 秒自动全平 |
| `notify` | true | 飞书提醒 |

**⚠️ 参数陷阱**：

```
sustain_sec = 1 且 auto_close_sec = 1
→ 达标后约 2 秒就全平
→ 浮盈 180 U 时就被砍了（刚过 200 又回落）
```

**建议**：`sustain_sec` 设 30-60 秒，`auto_close_sec` 设 ≥60 秒或 0（只提醒不自动平）。

**手动重置**：

前端风控页有两个按钮：
- 【今日重置】：清状态 + 当天不再自动触发 + 解锁开仓
- 【重新启用】：只清状态，下一轮 tick 会重新判断

对应 API：
```bash
POST /api/daily-target/reset {"skip_today": true}   # 重置并跳过今天
POST /api/daily-target/reset {"skip_today": false}  # 只重置
```

**注意**：`skip_today` 会写入数据库，重启后仍然有效。

**详细说明**：`docs/日目标设置说明.md`

## 影子系统

**作用**：验证「如果当时按另一套规则走，结果会怎样」。

**机制**：

不管信号有没有真的开仓，都记录下来，然后用虚拟仓位跟踪它后续的表现。

**记录的三套规则**：

| 规则 | 说明 |
|---|---|
| R1 | 无额外过滤，被拦就记录 |
| R2 | 加「无持仓冲突」过滤 |
| R3 | 加「方向不冲突」过滤 |

**当前结论**（2026-11-05）：

```
多头：202 笔，胜率 84.2%，平均 +1.111R，累计 +224.4R
空头： 60 笔，胜率  0.0%，平均 -1.012R，累计  -60.7R
```

**空头 0% 胜率的解读**：这是**当前行情单边上涨**导致的，不是策略缺陷。
系统实际没有开空单（风控拦截），所以不影响实盘。

**档案**：`docs/SHADOW_SYSTEM.md`

## 配置文件说明

### `strategies.yaml`

**分四段**：

```yaml
# ── 1. 全局风控 ──
global:
  max_concurrent_coins: 8        # 并发币种上限
  max_same_side: 6               # 同方向上限
  risk_per_trade_pct: 0.5        # 每单风险 %
  daily_loss_halt_pct: 10        # 熔断线 %（6 个仓位同时止损 = 9%）
  max_gross_leverage: 6          # 总杠杆上限（6 个 × 9380U = 5.62x）
  max_position_pct_per_coin: 32  # 单币名义上限 %（不改这个，风险比例会被截断）
  event_quiet_minutes: 30        # 事件静默窗口

# ── 2. 策略实例 ──
strategies:
  S15_CE_ZLSMA:
    enabled: true
    scan_interval: 15m           # 该字段已废弃，实际由 params.kline_interval 决定
    max_hold_hours: 16
    params: { ... }

# ── 3. 币种池 ──
pools:
  candidate:
    size: 200
    min_amp_pct: 10
    max_amp_pct: 300
  monitor:
    size: 23                     # 上限，两档交替补位
    min_quote_vol: 10000000
    max_spike: 4.0               # 日线口径
    atr_enter_min: 1.20          # 进池线：5m ATR 严格大于才进
    atr_exit_max: 0.80           # 清退线：满30分+未持仓时跌破就移除
    # 已进持仓池的币不受 ATR 影响（出场交给策略层）
    min_dwell_sec: 1800          # 最短停留 30 分钟
    atr_interval: 5m
    bbw_interval: "off"          # 加引号！裸写 off 会被 YAML 解析成 False
    refresh_sec: 180             # 池内刷新 3 分钟
    scan_sec: 900                # 池外刷新 15 分钟
    daily_refresh_sec: 86400

# ── 4. 币种白名单 ──
universe:
  whitelist: [BTCUSDT, ETHUSDT]
```

**热重载**：改完 `strategies.yaml` 保存即可，引擎每 0.5 秒重新读取。
**风控参数**改完立即生效，**正在持仓的仓位不受影响**。

## 回测

```bash
# 下载 30 天历史数据（币安部分序列仅保留 30 天，建议尽快执行）
python -m backend.backtest download

# 单策略默认参数回测
python -m backend.backtest run --sid S15_CE_ZLSMA

# 完整管线：网格搜索 + IS/OOS 验证 + 报告
python -m backend.backtest all --workers 6
# -> backtest/reports/<日期>/SUMMARY.md + 各策略报告
#    + strategies.suggested.yaml（不会改动你的生产配置）
```

**方法论要点**：

- 模块注入方式**回放实盘策略代码**（零逻辑漂移）
- 因子仅用已完结数据桶（**构造性防未来函数**）
- 出场按同 bar 悲观规则
- 成本含 taker 手续费、分档滑点与真实资金费结算
- 选参用**邻域高原中位数**而非单点最优（防过拟合）
- OOS 仅对入选参数运行一次

## 观察期与优化路线

系统自 **2026-11-06 傍晚 ~ 11-13** 处于**观察期**（跑一周看实际情况）。

> **为什么重置**：11-06 一天里动了三件会改变交易结果的事 ——
> ① 三模块架构改造（池子/门槛/价格口径全换）② 出场规则改成「2R 平一半」
> ③ 风控从 0.5% / 8 并发 / 3x 杠杆改成 1.5% / 6 并发 / 6x 杠杆。
> 每一项都让旧数据不可比，所以从最后一次改动生效时刻重新起算。
> 基线 **10,005.03 U，0 持仓**。

### 本周定案的配置（冻结，跑一周不改）

| 项 | 值 |
|---|---|
| 单笔风险 | **1.5%**（1R ≈ 150 U） |
| 同时持仓 | **最多 6 个** |
| 总杠杆 | **6x**（6 个满仓 = 5.62x） |
| 单币名义上限 | 权益 × 32% × 6 |
| 止损 | 20 根阶段低点 |
| 到 2R | **平一半**，剩一半放开跑 |
| 趋势反转 | 连破 2 根 ZLSMA + 回撤 0.8R → 全平 |
| 时间止损 | 16h（已平一半的豁免） |
| 日熔断 | 10%（6 个同时止损 = 9%） |
| 日目标 | 800 U（= 5.33R，回测触发率 14.5%） |

**冻结内容**：
- ❌ 不调参数
- ❌ 不改代码逻辑
- ❌ 不扩数据采集
- ❌ 不开实盘

**允许**：纯展示层 UI 修复、纯正确性 bug 修复（不改变交易行为的）

**目的**：拿到干净的样本，判断这套规则在真实行情里能不能站住。

**及格线**：交易笔数 ≥15 笔 / 净R ≥0 / 最大回撤 ≤−8R / 胜率 ≥38%

**自动熔断**（触发即停手）：
- 净值跌破 **7,000 U**（回测最低 7,058，跌破说明超出历史最差）
- 连亏 **10 笔**
- 池外币被开仓

> ⚠ 注意：熔断线的口径会随风险比例变化。0.5% 时代写的 9,600 U（−4%）
> 在 1.5% / 6 并发下已经不合适 —— 单笔波动就是 1.5%，−4% 只够两次半。
> 现在按「回测最大回撤 2,947 U，再留一点余量」定在 7,000 U。

## 常见问题

### Q: 为什么一直是 0 仓位，不开单？

检查顺序：

1. **候选池有没有币**：看 `/api/pool`，`candidate_n` 应该是 200
2. **监控池有没有币**：`/api/pool` 里 `in_monitor` 的应该有 40-69 个
3. **是不是熔断了**：`/api/status` 里看 `halted`
4. **是不是日目标已达成**：看 `daily_target.state`
5. **卡在哪道闸**：看总览页「三道光闸」tab，它直接告诉你每个币卡在 CE / HA / BBW 哪一步

### Q: 为什么某个币一直被拦？

看 `/api/signals` 的 `reason`：

| reason | 含义 |
|---|---|
| `杂讯过滤:量小` | 24h 成交额 < 1000 万 U |
| `杂讯过滤:易插针` | 插针比 > 4.0 |
| `杂讯过滤:未进监控池` | 5m ATR ≤ 1.20% / 成交额 < 1,000 万 / 插针 > 4.0 / 容量已满 |
| `同币已有仓位` | 该币已有仓位（禁止加仓和对锁） |
| `并发币数已达上限` | 已有 6 个仓位 |
| `多头方向已达上限(6)` | 多头已有 6 个 |

### Q: 权益曲线和实际持仓对不上？

权益曲线是**每 10 秒**采样一次，持仓浮动盈亏是**实时**的。在快速行情里会有 1-2 个采样点的偏差，属正常。

### Q: 能同时跑多个策略吗？

能。`strategies.yaml` 的 `strategies` 段可以写多个实例，每个独立参数、独立资金、独立币种范围。

**但注意**：风控是**全局**的。多个策略共享 8 个并发名额。

### Q: 回测结果和实盘差很多？

常见原因：

1. **手续费**：默认 0.05%，实际币安 taker 0.04%、maker 0.02%
2. **滑点**：回测假设按收盘价成交，实盘有滑点
3. **资金费率**：持仓过夜要付资金费，回测里可能没算
4. **信号延迟**：回测是「K 线收盘立刻成交」，实盘有网络延迟

### Q: 数据库在哪？

`quantbot.db`（项目根目录）。**已被 `.gitignore` 排除，不会提交。**

备份：直接复制这个文件即可（SQLite 单文件）。

## 流量说明

系统曾有 56 个因子采集器（27 种 × 30 币），每天产生 20-30 GB 流量。

实测这些数据策略一个都不用（S15 只用 K 线与价格），已全部关闭，**只保留 `mark_all`（现价快照）**。

**当前流量账**：

| 数据 | 频率 | 每天 |
|---|---|---|
| 成交额 + 插针（日线） | 每天 1 次 | 4 MB |
| 5m ATR · 池内 | 3 分钟 | 33 MB |
| 5m ATR · 池外 | 15 分钟 | 51 MB |
| 全市场行情 `mark_all` | 30 秒 | 143 MB |
| **合计** | | **约 231 MB/天** |

若需重新启用某个因子：

```python
import sqlite3
c = sqlite3.connect('quantbot.db')
c.execute("INSERT OR REPLACE INTO meta(key,value) VALUES(?,?)",
          ('factor_enabled:因子名', '1'))
c.commit()
```
